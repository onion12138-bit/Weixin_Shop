# Fixed-View 2.5D Manual Vertical Slice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an administrator upload, preview, publish, and roll back fixed-view transparent bead assets, then let the WeChat mini program compose those assets into a performant 2.5D bracelet with deterministic fallbacks.

**Architecture:** Add versioned bead visual assets to the catalog module and a small global visual configuration to the DIY module. Public catalog responses expose only the visual version currently referenced by the bead SKU; the mini program keeps its ordered SKU array and Canvas 2D editor, but delegates draw ordering and shadows to a pure TypeScript renderer. This plan deliberately delivers a complete manual-upload path before any Blender dependency.

**Tech Stack:** Java 17, Spring Boot 3.2.12, MyBatis-Plus 3.5.7, Flyway, MySQL 8, Java ImageIO plus a bounded PNG/WebP header inspector, Vue 3.5, TypeScript 5.7, Vitest, native WeChat Canvas 2D, Jest.

## Global Constraints

- The customer sees a fixed-view 2.5D bracelet; do not add GLB, glTF, Three.js, WebGL, free rotation, AR, or real-time PBR.
- The ordered SKU ID array remains the only persisted DIY design source of truth.
- `cover_asset_id` remains the commerce cover; do not reuse it as the DIY visual asset.
- Manual upload and published-asset fallback must work when Blender is absent or disabled.
- Only an explicitly published visual is returned to the mini program.
- Public visual fallback order is `canvasUrl → coverUrl → color placeholder`; tray fallback order is `trayUrl → coverUrl → color placeholder`.
- Automatic and manual asset revisions never overwrite a published binary; publication updates a version pointer transactionally.
- Visual failures must not affect price, quote fingerprints, inventory, BOM, orders, or fulfillment.
- Canvas output is fixed-view and front-facing; runtime configuration is limited to background, bracelet shadow, bead shadow, and overlap ratio.
- Preserve all unrelated uncommitted workspace changes. Stage and commit only files listed by the current task.
- Follow TDD: every behavior change starts with a failing focused test, and every task ends with a focused commit.

- [ ] **Step 5: Implement transactional version creation and publication**

`createManual` must:

1. Require the SKU and both active assets.
2. Validate 160×160 tray and 512×512 canvas images with alpha.
3. Compute `versionNo = max(existing.versionNo) + 1` while locking the SKU row.
4. Insert `sourceType=MANUAL`, `status=READY`, and the authenticated `Authentication.getName()`.

`publish` must use one transaction:

```java
BeadSku bead = requireLockedBead(skuId);
BeadVisualVersion candidate = requireLockedVersion(versionId);
requireBelongsTo(candidate, bead);
requireStatus(candidate, BeadVisualStatus.READY);
requirePublishableAssets(candidate);

Long previousId = bead.getPublishedVisualVersionId();
if (previousId != null) {
    BeadVisualVersion previous = versionMapper.selectByIdForUpdate(previousId);
    previous.setStatus(BeadVisualStatus.ARCHIVED);
    versionMapper.updateById(previous);
}
candidate.setStatus(BeadVisualStatus.PUBLISHED);
candidate.setPublishedBy(actor);
candidate.setPublishedAt(LocalDateTime.now(clock));
versionMapper.updateById(candidate);
bead.setPublishedVisualVersionId(candidate.getId());
beadSkuMapper.updateById(bead);
```

`rollback` must not reactivate an archived row. It creates a new `MANUAL/READY` version that references the selected historical assets, then publishes the new version in the same service call.
