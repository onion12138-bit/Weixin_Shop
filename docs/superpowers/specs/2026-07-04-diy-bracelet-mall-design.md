## 2. 建设目标

建设一个可以真实使用和持续迭代的 DIY 手串定制商品系统，而不是只包含静态页面的演示原型。

V1 需要同时交付：

1. 顾客使用的原生微信小程序；
2. 运营人员使用的 Vue 3 管理后台；
3. 提供真实数据、业务规则和权限控制的 Spring Boot 服务；
4. MySQL、Redis、本地文件存储和可重复初始化的演示数据；
5. 完整的项目总览、需求、架构、数据、API、开发、部署和测试文档。

V1 的核心业务闭环为：

> 浏览商品或套餐 → DIY 排珠 → 实时计价和规则推荐 → 保存方案与预览图 → 创建订单并预占库存 → 模拟支付或后台确认 → 生成生产 BOM → 后台履约 → 用户确认收货

## 4. 总体架构

### 4.1 架构选择

采用模块化单体架构：

```text
原生微信小程序 ─┐
                 ├─ REST API ─ Spring Boot 模块化单体 ─ MySQL 8
Vue 3 管理后台 ──┘                         ├─ Redis 7
                                           └─ 本地文件目录
```

选择模块化单体的原因：

- 当前团队和业务规模不需要微服务带来的部署与运维复杂度；
- 订单、库存和计价需要清晰的本地事务边界；
- 按业务模块分包可以保留未来拆分能力；
- 三端可以围绕同一份接口契约稳定迭代。

### 4.2 后端模块边界

后端按业务能力分包，不按 Controller、Service、Mapper 建立全局横向大目录。

- `auth`：登录、JWT、RBAC 和当前用户上下文；
- `user`：顾客、地址和个人资料；
- `catalog`：分类、珠子 SKU、套餐和素材；
- `diy`：方案、方案明细、预览图和编辑器数据；
- `pricing`：珠子费用、工艺费、配件费和优惠计算；
- `recommendation`：规则推荐、寓意模板和 AI 适配接口；
- `inventory`：可售库存、预占、释放、实扣和库存流水；
- `order`：订单聚合、状态机、快照、取消和支付确认；
- `production`：BOM、生产任务、指导图和发货；
- `subscription`：缺货订阅和通知任务；
- `file`：文件元数据、本地存储和云存储适配接口；
- `admin`：后台权限、系统配置、审计和统计；
- `shared`：通用错误、返回结构、分页、安全和基础设施配置。

模块之间通过明确的应用服务接口或领域事件协作，不允许跨模块直接修改对方数据表。

### 4.3 外部能力适配

以下能力采用端口与适配器模式：

| 能力 | V1 默认实现 | 后续实现 |
|---|---|---|
| 顾客身份 | 本地演示登录 | 微信 `code2Session` |
| 支付 | 模拟支付、后台确认 | 微信支付 V3 |
| 文件存储 | 本地文件目录 | 腾讯云 COS / 阿里云 OSS |
| 寓意生成 | 规则和模板 | 豆包 API |
| 通知 | 站内待通知记录 | 微信订阅消息 |

业务服务仅依赖能力接口，不依赖具体 SDK。

## 6. 数据模型

### 6.1 用户与权限

- `user_info`：顾客账号、昵称、头像、状态和会员信息；
- `user_address`：收货人、联系方式、地区和详细地址；
- `admin_user`：管理员账号、密码摘要和状态；
- `admin_role`：角色；
- `admin_permission`：菜单和接口权限；
- `admin_user_role`、`admin_role_permission`：关联表；
- `admin_operation_log`：后台关键操作审计。

### 6.2 商品与 DIY

- `category`：商品分类；
- `bead_sku`：珠子材质、颜色、直径、售价、成本、库存阈值、标签和状态；
- `product_package`：成品套餐；
- `package_item`：套餐中的有序珠子和配件；
- `asset_file`：本地或云端文件元数据；
- `diy_scheme`：用户方案、手围、圈数、绳色、预估价格和预览图；
- `diy_scheme_item`：方案中的有序珠子与数量。

标签使用规范化关联表或 JSON 数组取决于查询方式。需要参与筛选和推荐的标签采用关联表，展示型扩展属性可使用 JSON。

### 6.3 计价与推荐

- `craft_fee_rule`：按珠子数量区间配置工艺费；
- `accessory_sku`：绳、隔片和包装等配件；
- `recommend_rule`：推荐维度、条件、优先级和生效状态；
- `recommend_rule_item`：规则命中的珠子或套餐；
- `meaning_template`：寓意文案模板；
- `system_config`：非敏感业务配置。

### 6.4 库存、订单与生产

- `inventory_stock`：SKU 可用、预占和实际库存；
- `inventory_reservation`：订单维度的库存预占记录；
- `inventory_transaction`：入库、预占、释放、实扣和调整流水；
- `order_info`：订单金额、地址快照、状态、支付方式和时间；
- `order_item`：订单中的珠子、套餐、配件和数量快照；
- `order_status_log`：每次状态迁移；
- `payment_record`：模拟或真实支付记录与幂等键；
- `production_task`：生产任务、BOM、指导图和履约状态；
- `stock_subscribe`：缺货订阅和通知状态。

金额统一使用 `decimal(12,2)` 和 Java `BigDecimal`，禁止使用浮点数计算金额。

## 7. 核心业务流程

### 7.1 DIY 与计价

1. 小程序加载已上架 SKU、套餐、配件和必要价格信息；
2. Canvas 按珠子有序数组计算坐标并绘制；
3. 客户端进行即时预估，减少交互延迟；
4. 保存方案或下单前调用后端计价接口；
5. 后端重新读取有效价格和工艺费规则，返回权威报价；
6. 下单时将商品名称、图片、单价、数量、顺序、工艺费和总价保存为快照。

客户端价格只能用于展示，不能作为订单最终金额。

### 7.2 推荐

1. 用户选择星座、五行、生肖、心愿、场景和预算；
2. 后端匹配启用的推荐规则和真实可售库存；
3. 生成最多三组可编辑方案；
4. V1 使用模板组合寓意文案；
5. 后续 AI 适配器只负责自然语言解析和文案生成，不能直接生成 SKU ID。

### 7.3 库存预占与订单

1. 创建订单请求携带客户端幂等键；
2. 后端校验用户、地址、方案、价格和 SKU 状态；
3. 按固定顺序获取库存锁，防止并发死锁；
4. 在事务中写入订单快照、预占记录并增加预占数量；
5. 订单进入 `PENDING_CONFIRMATION`；
6. 模拟支付成功或管理员确认后，预占库存转为实际扣减；
7. 系统创建生产任务和 BOM 快照；
8. 待确认订单超时或用户取消时释放预占；
9. 已确认并进入生产的订单不能由用户直接取消。

### 7.4 订单状态机

```text
PENDING_CONFIRMATION
  ├─ CONFIRMED
  │    └─ IN_PRODUCTION
  │          └─ SHIPPED
  │                └─ COMPLETED
  └─ CANCELLED

CONFIRMED / IN_PRODUCTION / SHIPPED
  └─ REFUND_REVIEW / REFUNDED（仅后台售后流程）
```

所有状态变化必须通过状态机服务执行并写入状态日志，禁止直接更新状态字段。

### 7.5 生产履约

确认付款后生成不可变的 BOM 快照，包括：

- 有序珠子列表；
- 各 SKU 名称、规格、缩略图和数量；
- 手围、圈数、绳色和配件；
- 生产指导图；
- 收货地址快照；
- 订单备注。

后台可查看和打印 BOM，推进生产、发货和完成状态。

## 8. API 与权限设计

API 统一前缀为 `/api`：

- `/api/app/**`：小程序接口；
- `/api/admin/**`：管理后台接口；
- `/api/public/**`：无需登录的公开资源和健康检查。

统一返回包含：

- `code`：稳定业务错误码；
- `message`：可展示说明；
- `data`：响应数据；
- `traceId`：问题定位标识；
- `timestamp`：响应时间。

管理员接口使用角色和权限点控制；顾客接口必须校验数据所有权，禁止通过修改 ID 访问其他用户的方案、地址或订单。

## 9. 错误处理与数据一致性

- 使用 Bean Validation 处理字段和格式校验；
- 使用全局异常处理器统一转换错误；
- 业务异常使用稳定错误码，不把数据库异常直接返回前端；
- 订单创建、支付确认和库存释放使用幂等键；
- 订单、预占记录和库存更新处于同一事务；
- 库存锁按 SKU ID 排序获取；
- 任务重试必须保证幂等；
- 模拟支付和未来微信支付共用支付应用服务；
- 文件上传校验扩展名、MIME、大小和实际内容；
- 本地文件名由服务端生成，禁止直接使用用户路径；
- 日志中不得记录密码、Token、完整地址或支付敏感数据；
- 失败响应保留 `traceId`，后台日志记录完整原因。

## 10. 安全与合规

- 管理员密码使用 BCrypt；
- JWT 密钥通过环境变量提供；
- 生产环境禁止使用默认密码和演示账号；
- 管理接口启用 RBAC；
- 文件目录禁止执行脚本；
- CORS 仅允许配置的管理后台来源；
- 寓意、五行和运势文案展示“文化娱乐，仅供参考”；
- 下单页显著提示定制商品售后规则；
- 用户敏感信息遵循最小化收集原则；
- 数据导出和日志隐藏敏感字段。

## 15. 实施分解

项目按以下可独立验证的交付阶段实施，每个阶段单独编写实施计划并在通过验收后进入下一阶段：

1. **工程基础与商品目录**：完成仓库结构、运行环境、认证骨架、数据库迁移、本地文件、商品与套餐后端、后台管理页面和小程序浏览页面；
2. **DIY、计价与推荐**：完成 Canvas 编辑器、方案、权威计价、工艺费、规则推荐和寓意模板；
3. **订单、库存与生产**：完成地址、订单快照、库存预占、模拟支付、状态机、BOM、生产任务和履约页面；
4. **用户运营与产品加固**：完成缺货订阅、统计、审计、权限完善、性能、安全、全链路测试和部署文档。

阶段之间共享本设计规定的模型和接口边界，不重复创建互相冲突的设计文件。

## 16. 完成标准

满足以下条件才可称为 V1 完成：

- 三端代码均存在且能按照文档启动；
- 数据库迁移和种子数据可重复执行；
- 核心业务闭环使用真实后端和数据库；
- 模拟支付、本地文件和规则推荐可用；
- 管理后台可以持续管理商品、库存、规则、订单和生产；
- 小程序可以完成 DIY、保存、下单和订单查询；
- 关键单元、集成和冒烟测试通过；
- 不存在已知的越权、超卖或非法状态迁移问题；
- 项目权威文档完整且与实现一致；
- 复杂代码具备准确、详细且可维护的注释。
